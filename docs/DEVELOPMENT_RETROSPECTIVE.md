# condition/recommendation 도메인 개발 회고

`docs/recommendation_system.md`(현재 로직이 "무엇"인지)와 짝을 이루는 문서로, 그 로직이
"왜" 지금 모습이 됐는지 — 개발하면서 겪은 문제와 그때 했던 고민을 기록한다. 세부 수치·재현
과정은 `docs/how_to_calculate_metrics.md`, `docs/ROUTE_API_RATE_LIMIT_ISSUE.md`,
`docs/LOAD_TEST_REPORT.md`에 이미 있어서, 이 문서는 그 세 문서를 관통하는 "왜 이런 선택을
했는가"를 이어붙이는 데 집중했다. 자세한 근거가 필요하면 각 절에서 원본 문서로 링크해뒀다.

## 1. 지표 설계 — 정확한 데이터가 없을 때 무엇으로 대체할 것인가

가장 먼저 부딪힌 건 "원하는 지표를 그대로 구할 수 있는 원본 데이터가 없다"는 문제였다. 치안
지표가 대표적인 사례다.

### 1.1 행정동별 범죄율은 애초에 구할 수 없었다

안전 점수를 설계할 때 가장 직관적인 지표는 "그 동네의 실제 범죄 발생률"이었다. 그런데 조사해
보니 **행정동 단위 범죄 통계는 개인정보보호를 이유로 공개되지 않았고, 구(지역구) 단위까지만
구할 수 있었다.** 그래서 `gu_crime_stats`는 처음부터 `gu_code` 기준으로만 값을 갖고, 같은 구에
속한 모든 행정동이 이 값을 그대로 공유하는 구조로 설계했다(`docs/recommendation_system.md`
Part 1.4). 이건 "동 단위로 더 세밀하게 만들지 못한" 타협이 아니라, **애초에 그보다 세밀한
원본 데이터 자체가 존재하지 않아서** 나온 구조적 한계다.

### 1.2 그래서 행정동 단위로 존재하는 "예방 자원" 데이터로 보완했다

구 단위 범죄율 하나만으로는 같은 구 안의 동 간 차이를 전혀 표현할 수 없었다. 그래서 CCTV,
가로등, 지구대/파출소, 안심벨처럼 **행정동 단위로 실제 존재하는 안전 관련 시설 데이터**를
찾아 같이 반영하기로 했다 — 범죄 발생이라는 결과(outcome) 자체는 못 구해도, 그 발생을
예방/억제하는 자원의 밀도는 동 단위로 구할 수 있었기 때문이다.

### 1.3 그런데 이 보완 데이터의 품질이 또 문제였다 — 특정 동에 쏠림

막상 데이터를 받아보니 이번엔 **분포가 심하게 한쪽으로 쏠려 있었다.** CCTV만 해도 동당
3대인 곳부터 436대인 곳까지 있었다(`docs/how_to_calculate_metrics.md`). 이런 분포를 그대로
표준화(z-score)하면 소수의 극단값 동네가 전체 분포를 왜곡해버려서, "CCTV가 유독 많은 한두
동" 때문에 나머지 동들의 상대적 순위가 다 눌리는 문제가 생겼다.

**대응**: 표준화 전에 `log1p`(자연로그(1+x)) 변환을 한 번 거쳐서 극단값의 영향력을 완충했다
(`ScoreMath.log1p` → `zScore`, `docs/recommendation_system.md` Part 1.3). 경찰서/지구대는
한 번 더 특이한 케이스였는데, 관할구역이 행정동보다 넓어서 실제로는 인근에 있어도 많은 동이
`police_office_count = 0`으로 잡히는 데이터 한계가 있었다 — 이건 정규화로 해결되는 문제가
아니라서, 가중치를 상대적으로 낮게(15%) 주고 `log1p`로만 완충하는 선에서 타협했다.

### 1.4 최종적으로: "결과 지표" 40% + "예방 자원 근사치" 60%

```
raw = -0.40×z_crime + 0.20×z_cctv + 0.15×z_streetlight + 0.15×z_police + 0.10×z_bell
```

범죄율(구 단위, 유일한 실측 outcome)에 가장 큰 가중치(40%)를 줬고, 나머지 4개(행정동 단위,
어디까지나 "예방 자원"이라는 간접 proxy)는 그보다 낮게 나눠 배분했다. 이 가중치는 통계적으로
도출한 게 아니라 상식적 우선순위에 기반한 초기값이라는 걸 문서에도 명시해뒀다 — 나중에 실제
사건 데이터나 사용자 설문으로 검증/보정하는 걸 전제로 한 잠정치다.

**결국 남은 한계**: 같은 구 안에서는 범죄율 항목이 전부 동일하기 때문에, 동 간 안전 점수
차이는 사실상 CCTV/가로등/경찰서/안심벨 밀도 차이에서만 벌어진다. 이건 데이터 자체의 한계고,
지금 구조에서는 해소할 수 없어서 "이런 한계가 있다"는 것 자체를 문서에 남겨두는 쪽을 택했다.

## 2. 카카오 길찾기 API — 문서화되지 않은 레이트리밋과의 씨름

지표 설계가 "없는 데이터를 어떻게 근사할까"의 문제였다면, 통근 필터(`CommuteFilter`)는 반대로
"있는 API인데 얼마나 써도 되는지 알 수가 없다"는 문제였다. (전체 경위는
`docs/ROUTE_API_RATE_LIMIT_ISSUE.md`에 더 자세히 있다.)

### 2.1 첫 증상 — 갑자기 수백 건이 실패한다

통근 조건이 있는 추천 요청은 후보 행정동 전부(최대 426개)에 대해 카카오 대중교통 길찾기
API를 실시간으로 호출한다. 실제로 돌려보니 한 번에 최대 309/426건이 `API limit has been
exceeded` 에러로 실패했다. 처음엔 "일일 호출 쿼터를 다 써버렸다"고 추정했는데, 같은 요청을
1시간 안에 다시 돌려봤더니 실패 건수가 오히려 309건 → 248건으로 **줄어들었다.** 고정된
일일 쿼터가 거의 바닥난 상태였다면 반복할수록 성공 개수가 단조 감소해야 하는데 그렇지
않았다 — 이 가설부터 틀렸다는 걸 깨달았다.

### 2.2 카카오는 정확한 임계값을 공식적으로 알려주지 않는다

카카오 개발자 문서를 다시 찾아봤지만 일간/월간 쿼터만 명시돼 있었고, 초당 단기 호출 제한
같은 건 어디에도 없었다. 데브톡 커뮤니티에서도 "제휴 문의로 별도 안내"라는 답변만 확인됐다.
**비정상 트래픽을 방지하려는 의도로 임계값 자체를 공개하지 않는 것**으로 보였는데, 이게
당황스러웠던 지점이다 — 참고할 표준 스펙이 없으니 "얼마나 빠르게 호출해도 안전한지"를
스스로 실측해서 알아내는 것 말고는 방법이 없었다.

### 2.3 그래서 직접 실측했다

요청 순번과 시작/종료 시각을 로깅하도록 계측을 추가해 실패 패턴을 다시 들여다봤더니, 실패가
무작위가 아니라 **거의 정확히 벽시계 1초 간격으로 성공 구간과 실패 구간이 반복**되고 있었다
— 분당이 아니라 초 단위로 리셋되는 짧은 윈도우 제한이라는 뜻이었다. 이걸 확인하려고
`CountDownLatch`로 정확히 같은 시각에 10/15/20/25건씩 동시에 쏘는 실험을 했다.

| 동시 요청 수 | 결과 |
|---|---|
| 10 / 15 / 20 | 매번 전부 성공 |
| 25 | 20건은 성공, 나머지는 거의 결정적으로 거절 |

이 환경 기준 실측 상한이 **초당 약 20건**이라는 걸 이렇게 직접 알아냈다. 다만 이건 어디까지나
"우리 API 키·환경에서의 실측치"라 공식 보장이 아니고, 나중에 별개로 **일일 쿼터도 진짜로
존재한다**는 걸 다시 확인했다(당일 누적 호출량이 많아진 시점에 갑자기 이후 전부 실패하는
절벽형 패턴 → API 키 교체 후 해소). `-10 API limit has been exceeded`라는 에러 메시지 하나가
"초당 한도 초과"와 "일일 쿼터 소진"을 구분 없이 똑같이 내려주기 때문에, 응답만 봐서는 둘 중
뭐가 원인인지 알 수 없다는 것도 이번에 알게 됐다.

### 2.4 대응책 — 후보를 줄이고, 속도를 늦춘다

두 가지를 조합해서 적용했다.

1. **Haversine 직선거리 사전 필터**: 목적지와의 직선거리가 가까운 상위 50건만 실제 API 호출
   대상으로 삼는다. 완전성을 일부 포기하는 트레이드오프지만(50위 밖의 "직선거리는 멀지만
   직행 노선이 빠른" 후보를 놓칠 수 있음), 구현이 단순하고 새 인프라가 필요 없었다.
2. **애플리케이션 전역 pacing**: `AtomicLong` 기반 CAS 슬롯 예약으로, 이 애플리케이션
   인스턴스를 거치는 **모든 요청을 합쳐서** 최소 80ms 간격(=12.5 req/s)을 강제한다. 실측
   상한(20 req/s) 대비 안전 마진을 둔 수치다. 동시에 여러 사용자 요청이 들어와도 합계가
   이 상한을 넘지 않도록 보장하는 게 핵심이었다 — 요청 1건 안에서만 페이싱해서는 여러
   사용자가 겹칠 때 여전히 뚫릴 수 있기 때문이다.

실제 컨테이너에서 단일 요청 50건, 동시 사용자 2명(100건)으로 검증했고 둘 다 실패 0건·429도
0건으로 확인했다. 이 대응은 나중에 3장에서 다시 등장한다.

## 3. 부하테스트로 발견한 데드락, 그리고 다시 마주친 레이트리밋 문제

동시 사용자가 몰려도 버티는지 미리 확인하려고 k6로 부하테스트를 진행했다(전체 과정은
`docs/LOAD_TEST_REPORT.md`). 여기서 새로운 버그를 발견했고, 그걸 고치는 과정에서 2장의
레이트리밋 이슈를 다시 만났다.

### 3.1 VU 20대부터 4.37%가 실패한다 — 데드락

동시 사용자(VU)를 5→10→20→50명까지 늘려가며 조건 생성/재계산을 반복시켰더니, VU가 20을
넘어가면서 요청의 4.37%가 `DeadlockLoserDataAccessException`으로 실패했다. 원인은
`recommendations` INSERT가 `admin_dong_id`로 `admin_dongs`를 참조하는 FK 때문이었다 — 서로
다른 사용자의 추천 결과에 같은 "인기 있는" 동네가 자주 겹치는데, 두 요청이 그 동네들을
**서로 다른 순서로** 잠그려고 하면 순환 대기(데드락)가 생긴다. VU가 적을 땐 이 충돌이 우연히
일어날 확률이 낮아 안 보이다가, 동시 요청이 많아지면서 눈에 띄게 된 것이었다. k6나 테스트
설정 때문이 아니라, 실제 서비스에서 동시 사용자가 늘면 그대로 재현될 수 있는 진짜 버그였다.

### 3.2 처음 고친 방식이 레이트리밋 문제를 다시 불러왔다

데드락은 트랜잭션 전체를 롤백시키기 때문에, 복구하려면 그 작업 전체를 처음부터 다시
시작해야 한다. 그래서 `DeadlockRetry`라는 재시도 유틸을 만들었는데, **처음 구현에서는 조건
생성 흐름 전체(`createAndRecommend()`)를 이 재시도로 통째로 감쌌다.**

문제는 이 흐름 안에 데드락이 실제로 나는 `recommendations` INSERT뿐 아니라, **하드필터의
카카오 통근 API 호출과 reason 생성의 OpenAI 호출까지 같이 들어있었다는 것**이다. INSERT에서
데드락이 나서 재시도하면, 이미 끝난 카카오·OpenAI 호출까지 처음부터 다시 실행되는 셈이었다.
2장에서 카카오 레이트리밋으로 이미 한 번 크게 고생했던 전례가 있어서, **하필 데드락이 잘 나는
상황(동시 요청 몰림)이 카카오 API 호출도 몰리는 상황과 정확히 겹친다는 게 마음에 걸렸다** —
재시도가 레이트리밋을 더 쉽게 건드리게 만들 위험이 있었던 것이다. 게다가 부하테스트 내내
`ROUTE_MODE=stub`(카카오 API를 흉내만 내는 스텁)을 썼기 때문에, 이 문제 자체를 부하테스트로는
확인한 적도 없었다는 걸 뒤늦게 자각했다 — 즉 눈에 보이지 않는 채로 잠재해 있던 위험이었다.

### 3.3 그래서 계산과 반영을 코드 레벨에서 분리했다

`RecommendationService.generate()` 하나였던 메서드를 둘로 쪼갰다.

- **`compute(...)`** — 하드필터·스코어링·reason 생성(외부 호출 포함)만 하고 DB에 아무것도
  쓰지 않는다. 트랜잭션을 걸지 않는다 — 걸면 카카오/OpenAI 응답을 기다리는 동안 DB 커넥션을
  계속 붙잡아두게 되기 때문이다.
- **`persist(...)`** — `compute()`가 만든 결과를 DB에 반영한다. 이 메서드만
  `@Transactional`이고, `DeadlockRetry`도 이 메서드를 호출하는 지점에서만 건다.

조건 저장 로직도 `UserConditionWriter`라는 별도 빈으로 뺐다(같은 클래스 안에서
`this.method()`로 `@Transactional` 메서드를 부르면 프록시를 안 거쳐서 트랜잭션이 안 걸리는
self-invocation 문제 때문에, 애초에 다른 빈으로 분리해야 한다).

### 3.4 분리하고 나니 새로운 문제가 생겼다 — 그리고 그것도 고쳤다

저장(트랜잭션 있음) → 계산(트랜잭션 없음, 외부 호출) → 반영(트랜잭션 있음 + 재시도)이 이제
서로 다른 트랜잭션 경계를 가지게 되면서, **저장이 이미 커밋된 뒤에 계산이나 반영이 실패하면
"추천 결과 없는 조건"만 남는 고아 상태**가 생길 수 있게 됐다. 예전에는 전부 한 트랜잭션이라
이런 부분 실패가 없었는데, 트랜잭션을 쪼갠 대가로 새로 생긴 문제였다.

처음에는 "이 경우가 드물게만 일어날 것"이라는 이유로 트레이드오프로 받아들이고 넘어가려
했는데, PR 리뷰에서 "확률이 낮다고 정책 없이 방치하면 안 된다"는 지적을 받아 실제 정리
정책을 추가했다. `createAndRecommend()`가 계산/반영 단계를 `try-catch`로 감싸서, 실패하면
방금 만든 조건을 하위 테이블부터 순서대로 지우는 보상 삭제(compensating delete)를 수행한 뒤
원래 예외를 그대로 다시 던지도록 했다. `recompute()`는 이 처리가 필요 없다 — 기존
`recommendations`를 DELETE+INSERT로 교체하는 `persist()`가 실패해도 그 자체가
`@Transactional`이라 기존 값이 롤백되어 그대로 남기 때문에, 애초에 고아 상태가 생기지 않는다.

#### 3.4.1 그 보상 삭제 자체에도 구멍이 있었다

정리 정책을 넣고 나서도 끝이 아니었다. 처음 구현에서는 `compute()`/`persist()` 호출뿐 아니라
그 결과를 응답 DTO로 변환하는 `toResponse(...)`까지 같은 `try` 블록 안에 있었다. `toResponse`는
DB를 전혀 건드리지 않는 순수 변환 함수라 "그 안에서 예외가 날 일이 뭐가 있겠나" 싶어서 딱히
경계를 나누지 않았던 건데, 이게 진짜 문제로 이어졌다.

`persist()`가 이미 성공해서 `recommendations`/`recommendation_scores`가 **커밋까지 끝난 뒤**,
`toResponse()`에서 예외가 나면 여전히 같은 `catch` 블록이 걸려서 보상 삭제가 실행됐다. 그런데
`UserConditionWriter.delete()`는 `recommendations`를 지우는 로직이 없다 — 애초에 "저장이
실패했을 때" 되돌리기용으로 설계된 거라 그 시점엔 `recommendations`가 존재할 거라고 가정하지
않았다. 그 결과 이미 커밋된 `recommendations`가 `admin_dong_id` FK로 `user_conditions`를
참조하고 있는 상태에서 `user_conditions` 삭제를 시도하다 그 자체가 실패했고, 이 삭제 실패는
"삭제 자체가 실패해도 원래 예외를 가리지 않는다"는 방어 로직에 의해 조용히 로그만 남기고
삼켜졌다. 결과적으로 **하위 테이블(가중치 등)만 사라지고 `user_conditions`와
`recommendations`는 그대로 남는, 처음 의도한 것보다 더 나쁜 반쯤 망가진 상태**가 만들어질 수
있었다.

이것도 PR 리뷰에서 지적받아 고쳤다 — `toResponse()` 호출을 `try` 밖으로 빼서, 보상 삭제
대상을 정말로 "DB에 아직 커밋 안 된 실패"(compute/persist)로만 좁혔다. 되짚어보면 "이 함수는
DB를 안 건드리니까 안전하다"는 판단 자체는 맞았는데, **그 함수가 놓인 위치(이미 커밋된 뒤)가
문제였다** — 순수 함수인지 아닌지가 아니라, 그 함수가 실패했을 때 "지금 여기까지 뭐가 이미
커밋됐는가"를 기준으로 정리 범위를 그어야 했다는 걸 뒤늦게 배웠다.

### 3.5 결과

수정 후 다시 부하테스트를 돌린 결과, 조건 생성 실패율이 **4.37% → 0.06%**로 떨어졌다.

## 4. 돌아보며

세 가지 문제(치안 지표, 카카오 레이트리밋, 데드락)를 관통하는 공통점이 하나 있다 — **명시된
스펙이나 완전한 데이터가 없는 외부 제약과 부딪힐 때마다, 그 자리에서 직접 실측하거나 대체
데이터로 근사하는 과정을 거쳤다는 것.** 행정동별 범죄율이 없으면 구 단위 값 + 행정동 단위
예방 자원으로 근사하고, 카카오가 레이트리밋을 공개하지 않으면 직접 벽시계를 재서 실측
상한을 알아내고, 데드락 재시도 범위를 어디까지 잡아야 안전한지도 실제로 두 번 겪어보고서야
정확한 경계(외부 호출 vs DB 반영)를 찾을 수 있었다.

특히 3장은 "한 문제를 고치려다 이미 겪었던 다른 문제를 다시 건드릴 뻔했다"는 사례라 기록해둘
가치가 있다고 판단했다 — 트랜잭션 경계와 외부 API 호출 경계는 처음부터 같이 고려해서
설계했어야 했는데, 데드락이라는 새 문제에 대응하다 보니 그 둘이 얽혀 있다는 걸 뒤늦게
알아차렸다. 다음에 비슷하게 "재시도"나 "트랜잭션 범위"를 다룰 일이 생기면, 그 범위 안에
느리거나 외부 자원에 의존하는 호출이 섞여 있지는 않은지부터 먼저 확인하는 게 좋겠다는 게
이번에 얻은 교훈이다.
