# condition/recommendation 도메인 — 추후 발전 방향

지금 당장 처리할 작업이 아니라, "나중에 이렇게 발전시키고 싶다"고 논의된 방향을 모아둔
문서다. 각 항목은 (1) 왜 필요한지, (2) 지금 상태, (3) 어떤 방향을 검토 중인지, (4) 아직
정해지지 않은 열린 질문 순으로 정리했다. 실제 착수 시점에 이 문서를 다시 열어 설계를
구체화하면 된다.

---

## A. 지표 데이터의 정확도·최신성

### A-1. 지표 테이블 세분화

**왜**: 지금은 하나의 `_count` 컬럼에 여러 성격의 장소가 뭉쳐 있어서, 사용자에게 실제로
와닿는 차이를 놓친다. 예를 들어 `nature_metrics.nature_count`는 `RIVER`/`TRAIL`/`PARK` 3개
카테고리를 합산한 값 하나뿐이다(`docs/recommendation_system.md` Part 1.2). "공원이 많은
동네"와 "산책로가 많은 동네"는 사용자에게 분명히 다른 의미인데, 지금 구조에서는 구분이
안 된다.

**방향**: `nature_metrics`를 `park_count`/`trail_count`/`river_count`로 나누는 것처럼, 여러
카테고리가 뭉쳐 있는 지표 테이블들을 세분화한다. 계산 로직(`DensityMinMaxScoreCalculator`)은
이미 `life_convenience`(마트/은행/백화점)처럼 여러 카운트 항목을 다루도록 만들어져 있어서,
`counts` 맵에 항목만 늘리면 계산기 자체는 그대로 재사용할 수 있다 — 새로 짜야 하는 건 스키마
마이그레이션과 매퍼 SQL, 그리고 `toInput()` 매핑 정도다.

**열린 질문**:
- 세분화한 컬럼을 사용자에게도 노출할지(우선순위 선택지를 "자연" 하나에서 "공원"/"산책로"로
  쪼갤지), 아니면 내부 계산에만 쓰고 최종 노출은 지금처럼 합쳐서 보여줄지
- 세분화 대상이 `nature`만인지, 다른 테이블(`healthcare`의 병원/약국, `food`의 음식점/카페
  등)도 같이 검토할지 — 지금은 nature가 가장 뭉뚱그려져 있어(3개 카테고리 → 1개 컬럼) 우선
  순위가 높다고 판단했다.

### A-2. 소음/범죄율 계산을 외부 API 연동 시점에 자동화

**왜**: 지금 `silence_metrics.silence_score`와 `gu_crime_stats.crime_rate`는 계산 로직이
코드로 존재하지 않고(또는 존재하더라도) 외부에서 값을 받아와 수동으로 적재하는 방식에
의존한다. 나머지 8개 지표(`places` 기반)는 데이터 수집부터 점수 계산까지 전부 애플리케이션
안에서 자동으로 돌아가는데, 이 둘만 수동 개입이 필요해 최신성이 떨어진다.

**방향**: 외부 데이터 소스(예: 서울 열린데이터광장의 소음 관측 자료, 경찰청/통계청의 구별
범죄 통계 API)를 호출해서 원본 값을 받아오는 시점에, 계산까지 같은 파이프라인에서 처리해
바로 `INSERT`하도록 만든다. 나머지 8개와 동일하게 `SilenceMetricScoreService`/구 단위 범죄율
서비스 형태로 `MetricAdminController`에 편입시키는 게 목표다.

**열린 질문**:
- 어떤 외부 API를 실제로 쓸지(안정성, 무료/유료 여부, 쿼터, 갱신 주기) 아직 조사 전이다.
- 소음 데이터는 기존 문서에 기록된 IDW 보간(결측치 31건을 최근접 5개 행정동으로 보간) 로직을
  그대로 코드화할지, 아니면 외부 API가 이미 보간된 값을 제공하는지에 따라 구현 범위가 달라진다.

### A-3. 지표/places가 갱신되면 `user_conditions.is_latest`를 `false`로 되돌리기

**왜**: 지금 `is_latest`는 조건 생성 시 기본값 `TRUE`로 시작해서, `recompute` 성공 시에만
다시 `TRUE`로 세팅되는 편도(one-way) 로직만 있다(`docs/recommendation_system.md` Part 2.7).
정작 "언제 `FALSE`가 돼야 하는지"—즉 지표나 `places`가 실제로 갱신돼서 예전 추천 결과가
낡았을 가능성이 생겼을 때 이걸 감지하는 로직이 없다. 그래서 사용자가 저장해둔 조건이 실제로
오래됐는지 지금은 알 방법이 없다.

**방향**: `MetricAdminController.recalculateAll()`이나 `places` 수집 스케줄러가 끝난 시점에,
영향받는 `user_conditions`(특히 `is_saved = TRUE`인 것들)의 `is_latest`를 일괄
`FALSE`로 갱신한다.

**열린 질문**:
- "영향받는 조건"의 범위를 어떻게 정할지 — 지표 갱신은 보통 전체 행정동에 한 번에 영향을
  주므로, 그냥 저장된 조건 전체를 갱신 대상으로 볼지, 아니면 조건의 `guCodes`/후보 행정동과
  갱신된 `admin_dong_id`의 교집합만 정밀하게 골라낼지(구현 복잡도 대비 실익을 따져봐야 함)
- 대량 `UPDATE`가 지표 재계산(10개 서비스, 매번 실행)마다 반복되는데 비용이 부담될지
- 프론트에서 `is_latest = FALSE`를 어떻게 보여줄지("결과가 오래됐어요, 다시 계산해보세요"
  같은 안내 UI가 필요해짐) — 이건 이 문서 범위 밖이지만 백엔드 설계에 영향을 준다.

### A-4. (추가 제안) 지표 재계산 스케줄러 도입

**왜**: 지금 지표 재계산은 `MetricAdminController`의 수동 관리자 엔드포인트로만 트리거된다
(`docs/recommendation_system.md` Part 1.5). 운영 환경에서 누군가 계속 수동으로 호출해주지
않으면 지표가 절대 갱신되지 않는다.

**방향**: `places`/전월세 수집 스케줄러처럼 `@Scheduled`로 주기적으로(예: 매일 새벽)
`recalculateAll()`을 자동 호출하도록 만든다. A-3(is_latest 갱신)과 자연스럽게 묶어서 설계하면
좋다 — 스케줄러가 재계산을 끝낸 시점이 곧 "영향받는 조건들의 is_latest를 갱신할 시점"이기
때문이다.

## B. 통근 필터의 확장성

### B-1. Haversine 상위 50개 캡의 완전성 보완

**왜**: `CommuteFilter`는 후보가 50건을 넘으면 목적지와의 직선거리 기준으로 가까운 상위
50건만 실제 카카오 API 호출 대상으로 삼는다(`docs/ROUTE_API_RATE_LIMIT_ISSUE.md`). 이건
카카오 API 호출량을 통제하기 위한 의도적 트레이드오프였지만, "직선거리는 멀지만 직행 노선이
있어 실제로는 빠른" 후보를 놓칠 수 있다는 완전성 손실이 그대로 남아있다.

**방향(검토 대상, 확정 아님)**:
- B-2(캐싱)가 쌓이면, 캐시로 이미 알고 있는 (출발동, 목적지동) 조합은 API 호출 없이도
  캡 안에 포함시킬 수 있어 실질적으로 캡을 상향할 여지가 생긴다.
- 직선거리보다 나은 사전 필터 기준을 재검토한다 — 예를 들어 지하철 노선도상 근접성(환승
  없이 도달 가능한 역 반경) 같은 걸 직선거리 대신/같이 쓰는 방법. `docs/
  ROUTE_API_RATE_LIMIT_ISSUE.md`의 "방안 2(행정동 경계 기반 사전 필터)"는 한 번 기각됐지만,
  그건 "구 경계" 기준이 부정확해서였지 "더 나은 사전 필터가 필요하다"는 문제의식 자체가
  틀린 건 아니었다.

**열린 질문**: 완전성을 얼마나 회복해야 "충분"한지에 대한 기준이 아직 없다 — 50건 캡이
실제로 추천 품질에 얼마나 영향을 주는지부터 측정(예: 캡을 100/200으로 늘렸을 때 상위 5개
추천이 얼마나 달라지는지)해보고 우선순위를 정하는 게 먼저일 수 있다.

### B-2. 길찾기 API 호출 캐싱

**왜**: 길찾기 API는 애플리케이션 전역 pacing(80ms 간격)으로 이미 스로틀링돼 있어서, 동시
사용자가 늘어날수록 이 pacing 자체가 병목이 될 가능성이 높다 — 사용자가 늘어도 초당 처리량
상한은 그대로 12.5 req/s이기 때문이다.

**방향**: `docs/ROUTE_API_RATE_LIMIT_ISSUE.md`에 이미 검토됐던 "목적지 행정동 단위 지연(lazy)
캐싱" 설계를 재추진한다 — 정확한 주소가 달라도 같은 행정동 안이면 `(출발 행정동, 목적지
행정동, 통근수단)` 단위로 캐시를 공유하는 방식이다. 전체 조합(426×426 ≈ 18만 쌍)을 미리 다
채우는 배치 방식은 그 자체로 지금 겪는 문제를 재현하는 규모라 이미 기각됐고, 실제 요청이
들어올 때만 필요한 만큼 채워나가는 지연 캐싱만 검토 대상이다.

**열린 질문(원래 문서에서 그대로 이어지는 것들)**:
- 캐시 TTL을 얼마로 둘지 — 통근시간은 도로/노선 변경으로 시간이 지나면 실제 값이 달라질 수
  있어서, 무한정 캐싱하면 안 됨
- 캐시 무효화 정책(수동/주기적 만료) 설계
- DB 스키마 초안은 예전에 준비했다가 이번 범위에서는 제외했다고 기록돼 있음 — 실제 착수 시
  다시 설계 필요

### B-3. (추가 제안) 대체/이중화 길찾기 API 검토

**왜**: 카카오 API 하나에만 의존하고 있어서, 카카오 쪽 장애나 레이트리밋이 곧 우리 서비스의
장애로 이어진다.

**방향**: `docs/ROUTE_API_RATE_LIMIT_ISSUE.md`에서 이미 검토했던 ODsay(전국 대중교통 길찾기
API)를 카카오 순간 장애/레이트리밋 시 폴백으로 병행 호출하는 이중화 전략을 재검토한다. 당시
문서에서는 "캐싱 도입 이후 효과를 측정해보고 필요성을 재평가"로 결론냈으므로, B-2가 먼저
진행되는 게 자연스러운 순서로 보인다.

## C. 추천 품질

### C-1. OpenAI 프롬프트 개선

**왜**: 지금은 토큰 비용 때문에 `recommendation.reason.mode`가 기본적으로 `stub`(고정
문구)이라(`docs/recommendation_system.md` Part 2.5), 실제 OpenAI 모드로 생성된 문구 품질을
운영 트래픽 기준으로 검증해본 적이 사실상 없다.

**방향**:
- 카테고리 점수 구간(예: 상위/중위/하위)에 따라 표현이 더 다양해지도록 few-shot 예시를
  프롬프트에 추가
- V8부터 저장되는 통근 상세(`route`/`lineNum`/`vehicleType` 등)를 reason 프롬프트에
  반영해서 "6호선으로 환승 없이 이동" 같은 더 구체적인 문구를 만들 수 있는지 검토(단, 지금
  프롬프트는 "구체적 사실을 지어내지 말라"는 제약이 있으므로, 실제 데이터 기반일 때만
  구체화하는 방향으로 신중하게 확장해야 함)
- `openai` 모드로 실제 트래픽 일부를 흘려보면서 품질/실패율(파싱 실패 → 플레이스홀더 폴백
  비율)을 실측

**열린 질문**: 토큰 비용과 품질 개선을 어느 선에서 맞출지에 대한 예산 논의가 먼저 필요하다.

### C-2. 리뷰 데이터·사용자 프로필 기반 개인화 추천

**왜**: 지금 추천은 전적으로 지표 z-score 가중합(`RecommendationScoreCalculator`)에만
기반하고, 사용자 개인의 히스토리(과거 조건, 찜한 동네, 다른 사용자가 남긴 리뷰)는 전혀
반영하지 않는다. "비슷한 조건을 찾은 다른 사용자들이 실제로 어떻게 평가했는지" 같은 정보가
빠져있다.

**방향(구체적 설계는 아직 없음, 방향성만)**:
- `reviews`(이미 존재하는 도메인)를 활용해, 후보 행정동에 달린 리뷰 감성/평점을 소프트
  스코어링에 추가 신호로 반영
- `favorite_dongs`(찜) 히스토리나 과거 저장 조건 패턴을 기반으로 한 협업 필터링 요소 검토

**열린 질문**:
- 콜드스타트 문제(리뷰/히스토리가 거의 없는 신규 서비스 초기 상태에서 이 신호가 얼마나
  유의미할지)
- 개인정보 관련 고려사항(사용자 히스토리를 추천에 쓰는 것에 대한 동의/투명성)
- 리뷰 데이터가 현재 얼마나 쌓여 있는지부터 확인 필요 — 이 문서 작성 시점 기준 별도 조사
  안 함

## D. 성능/운영 — 부하테스트에서 이미 식별된 후속 과제 (참고용)

`docs/LOAD_TEST_REPORT.md` 11장 "남은 과제"에 이미 기록된 항목들을 이 문서에도 모아둔다 —
condition/recommendation 도메인과 직접 관련 있는 성능 이슈라 여기서도 참조하기 쉽게 남겨둔다.

- **`MetricScoreMapper` 캐싱** — 소프트 스코어링이 추천 요청마다 9개 지표 테이블을 캐시
  없이 매번 통째로 조인해서 읽는다. 부하테스트에서 VU 150 근처부터 응답이 느려지는 원인으로
  지목된 지점이라, 성능을 더 끌어올리려면 이쪽이 우선순위가 높다.
- **JVM/애플리케이션 레벨 모니터링** — 이 프로젝트는 Spring Boot가 아니라 Spring MVC라
  Actuator/Micrometer가 없다. 지금은 k6 자체 지표와 MySQL 서버 지표만 볼 수 있어서, 힙
  메모리·GC·스레드풀 같은 JVM 내부 상태를 보려면 Prometheus JMX Exporter 도입이 필요하다.
- **피크시간 집중률 실측** — 실제 동시접속자 추정(현재 9~26명으로 추정)에 쓰인 "피크시간
  집중률" 값이 실측이 아니라 15~25% 가정치다. 팀 자체 조사(설문, 비슷한 서비스 벤치마크)로
  보정이 필요하다.

## E. 개발 중 발견한 그 외 정리 대상

이번 문서화 과정에서 코드를 다시 훑다가 눈에 띈, 위 항목들만큼 시급하진 않지만 언젠가
정리하면 좋을 것들이다.

- **`preferred_house_types`/`property_metrics`의 `house_type` ENUM에 `연립`/`다세대`/
  `연립다세대`가 있는데, `HouseTypeBudgetFilter.ALL_HOUSE_TYPES`(오피스텔/빌라/단독/다가구/
  아파트/원룸 6종)에는 빠져 있다.** 사용자가 이 3개 유형을 선택하면 예산 필터가 이걸
  전혀 고려하지 않는 것으로 보이는데, 의도된 것인지(아직 지원 안 하는 유형) 놓친 것인지
  확인이 필요하다.
- **`recommendation_scores`(카테고리별 breakdown)가 생성 시점에는 저장되지만, 저장된 조건을
  재조회하는 `GET /{conditionId}/recommendations`는 이 테이블을 다시 읽지 않는다** —
  프론트에서 "왜 이 동네가 추천됐는지" 카테고리별 상세를 재조회 화면에서도 보여주고 싶다면
  이 조회 경로를 추가해야 한다.
