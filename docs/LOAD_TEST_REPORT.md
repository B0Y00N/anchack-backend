# condition/recommendation 도메인 부하테스트 보고서

`test/load-test` 브랜치에서 진행한 condition/recommendation 도메인(조건 등록 및 동네 추천)
부하테스트의 전체 과정, 발견한 문제, 해결 방법, 그리고 그 근거를 정리한다. 부하테스트를 처음
접하는 사람도 읽을 수 있도록 용어와 계산 과정을 상세히 풀어썼다.

> **이 문서의 범위**: dev에는 운영 코드만 포함한다는 방침에 따라, 이 PR에는 부하테스트로
> 발견한 **데드락 버그 수정**과 **이 보고서**만 포함했다. 문서에서 언급하는 k6 스크립트,
> Prometheus/Grafana docker-compose 구성, `ROUTE_MODE` 스텁 전환 등 부하테스트 도구/코드
> 자체는 `test/load-test` 브랜치에 있으며 이 PR에는 포함되지 않는다.

---

## 1. 왜 이 작업을 했는가

condition/recommendation 도메인은 사용자가 원하는 조건(통근시간, 예산, 주거유형 등)을 입력하면
동네를 추천해주는, 이 프로젝트의 핵심 기능이다. 여러 명이 동시에 몰려도 앱이 버틸 수 있는지
미리 확인하고 싶어서 **부하테스트**를 진행했다.

**부하테스트(Load Test)란?** 실제 서버에 여러 명이 동시에 요청을 보내는 상황을 인위적으로
재현해서, 응답 속도가 얼마나 느려지는지·에러가 얼마나 나는지·어느 지점부터 문제가 생기는지를
미리 확인하는 작업이다. 실제 사용자를 기다렸다가 문제를 발견하는 대신, 출시 전에 스크립트로
"가짜 사용자 여러 명"을 만들어 미리 두드려보는 것이다.

## 2. 용어 설명 (먼저 읽어두면 이해가 빠르다)

| 용어 | 뜻 |
|---|---|
| **VU (Virtual User, 가상 사용자)** | 부하테스트 도구가 흉내 내는 "가짜 사용자" 한 명. VU 50이면 50명이 동시에 앱을 쓰는 상황을 흉내 낸다는 뜻. 실제 사람이 아니라 스크립트가 자동으로 요청을 반복해서 보내는 프로세스(정확히는 스레드)다. |
| **k6** | 이번에 사용한 부하테스트 도구(오픈소스). JavaScript로 "VU가 무엇을 몇 번 반복할지" 시나리오를 작성하면, 실제로 그만큼의 동시 요청을 만들어서 서버에 쏘고 결과(응답시간, 에러율 등)를 집계해준다. |
| **p50 / p95 / p99 (백분위수, percentile)** | 여러 번 측정한 응답시간을 빠른 순서로 줄 세웠을 때, 특정 위치의 값. p95=3초라는 건 "요청 100개 중 95개는 3초 이내에 끝났다(즉 최대 5%만 3초보다 오래 걸림)"는 뜻이다. 평균(avg)은 극단적으로 느린 소수 요청에 잘 안 흔들리지만, p95/p99는 "대부분의 사용자가 실제로 체감하는 최악의 경험"에 더 가깝기 때문에 부하테스트에서는 평균보다 p95/p99를 더 중요하게 본다. |
| **임계값 (threshold)** | "이 조건을 넘으면 실패로 본다"는 합격선. 예: `에러율 1% 미만`, `p95 3초 미만`. k6는 실행 중 이 조건을 계속 확인하다가, 넘으면 실행 결과를 실패로 표시하거나(옵션에 따라) 테스트 자체를 중단시킬 수 있다. |
| **HTTP 요청 실패율 (http_req_failed)** | 보낸 요청 중 정상 응답(200 등)을 못 받은 비율. 에러율과 같은 말로 썼다. |
| **처리량 (throughput, req/s)** | 초당 처리한 요청 개수. 높을수록 더 많은 트래픽을 감당한다는 뜻. |
| **DAU / MAU** | Daily/Monthly Active Users, 하루/한 달 동안 앱을 실제로 쓴 사용자 수. |
| **TAM / SAM / SOM** | 시장 규모를 좁혀가며 추정하는 단계. TAM(전체 잠재 시장) → SAM(우리 서비스가 실제로 노릴 수 있는 시장) → SOM(그중 우리가 실제로 확보할 수 있다고 보는 몫). 자세한 계산은 [9장](#9-실제-사용자-규모로-vu-추정하기)에서 다룬다. |
| **커넥션 풀 (Connection Pool)** | 앱이 데이터베이스(DB)와 매번 새로 연결을 맺으면 느리니까, 미리 몇 개의 연결을 만들어두고 재사용하는 것. "몇 개까지 미리 만들어둘지"가 **풀 크기(pool size)**다. 풀 크기가 10이면, 동시에 DB 작업을 할 수 있는 요청은 최대 10개뿐이고 11번째 요청부터는 앞의 요청이 끝나 커넥션을 반납할 때까지 기다려야 한다. |
| **데드락 (Deadlock)** | 두 개 이상의 작업이 서로 상대방이 붙잡고 있는 자원을 기다리며 영원히 멈추는 상황(순환 대기). DB는 이걸 감지하면 둘 중 하나(또는 여럿)의 작업을 강제로 취소시킨다. 3장에서 실제 사례로 자세히 설명한다. |
| **Docker / docker-compose** | 앱, DB 등을 각각 격리된 "컨테이너"로 실행하는 도구. `docker-compose.yml` 하나로 앱+DB+모니터링 도구를 한 번에 켜고 끌 수 있게 구성했다. |
| **Prometheus / Grafana** | Prometheus는 시간에 따라 변하는 수치(커넥션 수, 응답시간 등)를 주기적으로 수집해 저장하는 도구고, Grafana는 그 수치를 그래프로 보여주는 대시보드 도구다. "그때그때 로그로 확인" 대신 "시간 흐름에 따른 그래프"로 볼 수 있게 해준다. |

### 부하테스트의 여러 종류

한 번에 다 설명하지 않고, 아래에서 실행한 순서대로 그때그때 설명한다. 미리 감만 잡으면:

- **스모크 테스트**: "일단 정상적으로 동작은 하는지" 딱 1명으로 딱 1번 확인
- **부하테스트(write_heavy 등)**: 동시 사용자 수를 서서히 늘려가며 정해둔 최대치까지 버티는지 확인
- **혼합 시나리오**: 실제 사용자들이 쓸 법한 여러 기능을 섞어서 동시에 두드림
- **브레이크포인트 테스트**: "정확히 몇 명부터 무너지는지"를 찾을 때까지 계속 사용자 수를 늘림
- **소크 테스트**: 사용자 수는 적당히 유지한 채 오래(30분+) 돌려서 시간이 갈수록 느려지거나 메모리가 새는지 확인

## 3. 테스트 환경 준비

### 3.1 왜 별도 환경이 필요했나

이 도메인은 조건 생성 시 카카오 대중교통 길찾기 API를 호출하는데(통근시간 계산),
이 API에는 초당 호출 제한(약 12.5 req/s로 애플리케이션 내부에서 페이싱 처리됨,
[ROUTE_API_RATE_LIMIT_ISSUE.md](ROUTE_API_RATE_LIMIT_ISSUE.md) 참고)이 있다. 부하테스트로
수백~수천 건을 짧은 시간에 요청하면 이 제한에 걸려 "우리 서버 성능"이 아니라 "카카오 API
제한"을 테스트하게 되는 문제가 있었다.

### 3.2 ROUTE_MODE=stub — 카카오 API 없이 테스트하기

`RouteService` 인터페이스에 실제 카카오 API를 호출하는 `RouteServiceImpl`과, 호출 없이
고정값을 즉시 반환하는 `StubRouteService`(`test/load-test` 브랜치) 두 가지 구현체를 만들고,
환경변수 `ROUTE_MODE`(기본값 `kakao`)로 어느 걸 쓸지 전환할 수 있게 했다. 부하테스트 중에는
`.env`에 `ROUTE_MODE=stub`을 설정해 카카오 호출 없이 나머지 파이프라인(하드필터·스코어링·DB)만
순수하게 측정했다.

### 3.3 DB 준비

원격 개발 DB를 로컬 Docker MySQL로 복제했다(`users` 테이블 제외). 복제한 로컬 DB 기준
행정동(admin_dongs) 426개, 인프라 위치정보(places) 약 20만 건, 시세정보(property_metrics)
약 2,300건 규모다.

### 3.4 테스트 전용 유저 50명 시딩

조건 생성/조회 API는 로그인(JWT)이 필요하다. 실제 카카오 로그인을 매번 거칠 수 없어서,
부하테스트 전용 유저 50명(`user_id` 4~53, `provider_id`='k6-loadtest-001'~'050')을
`seed_k6_test_users.sql`(`test/load-test` 브랜치)로 미리 만들어뒀다.

### 3.5 로그인 없이 인증 토큰(JWT) 발급하기

이 앱은 로그인에 성공하면 JWT(JSON Web Token, 일종의 "이 사람은 로그인했다"는 서명된 증명서)를
발급하고, 이후 요청마다 이 토큰을 헤더에 담아 보낸다. k6 스크립트가 매번 실제 카카오 로그인을
거칠 수는 없으므로, 서버와 동일한 서명 비밀키(`.env`의 `JWT_SECRET`)로 k6가 직접 토큰을
만들어 쓰도록 했다(`auth.js`, `test/load-test` 브랜치). 서버 입장에서는 실제 로그인을
거친 토큰과 구분할 수 없어 정상적으로 인증된다.

## 4. 시나리오별 실행 결과

총 6개 시나리오를 만들어(`loadtest/k6/scenarios/`, `test/load-test` 브랜치) 순서대로
실행했다. 각 시나리오가 왜 필요한지, 무엇을 확인했는지, 결과가 무엇이었는지를 순서대로 적는다.

### 4.1 스모크 테스트 (00_smoke.js)

**목적**: 본격적인 부하를 걸기 전에, "애초에 정상적으로 동작은 하는지"를 VU 1명, 딱 1회만
돌려서 확인한다. 여기서 실패하면 이후 모든 시나리오 결과가 무의미하므로 항상 제일 먼저
돌린다.

**방법**: 조건 생성 → 저장 → 저장 목록 조회 → 추천 결과 조회 → 재계산 → (통근조건 포함)
생성 → 저장 취소, 총 7단계를 순서대로 호출하고 매 단계 응답을 검증한다.

**결과**: 12개 검증(check) 전부 통과. 평균 응답시간 74ms, 최대 179ms. 이후 시나리오를 진행할
기반이 마련됐다.

### 4.2 핵심 쓰기 경로 부하테스트 (01_write_heavy.js)

**목적**: 이 도메인에서 가장 무거운 두 작업 — 조건 생성(`POST /api/user-conditions`)과
재계산(`POST /{id}/recompute`) — 이 동시 사용자가 늘어도 버티는지 확인한다. 이 두 작업은
내부적으로 후보 동네를 걸러내고(하드필터), 9개 지표 테이블을 조인해 점수를 계산하고
(캐시 없음), 결과를 DB에 새로 써넣는(INSERT) 무거운 흐름을 매번 처음부터 반복한다.

**방법**: VU를 0명에서 시작해 5→10→20→50명까지 6분 30초에 걸쳐 서서히 늘리며(이런 방식을
**램핑(ramping)**이라 부른다) 계속 생성+재계산을 반복시킨다.

**첫 실행 결과 — 문제 발견**: VU가 20을 넘어가면서 생성 요청의 **4.37%(513/11,733건)가
실패**했다. 원인은 5장에서 자세히 다룬다.

**버그 수정 후 재실행 결과**: 실패율이 **0.06%(8/12,264건)**로 떨어졌다. p95 응답시간은
생성 911ms, 재계산 641ms로 임계값(5초) 대비 충분히 빨랐다.

### 4.3 읽기 경로 대조군 (02_read_baseline.js)

**목적**: 위 쓰기 경로와 비교할 "대조군"이 필요했다. 저장된 추천 결과를 다시 계산하지 않고
그대로 보여주는 조회 API(`GET /{id}/recommendations`, `GET /saved`)만 따로 떼어, 순수하게
DB 읽기 성능과 커넥션 풀 상태를 확인했다.

**방법**: 테스트 유저 20명의 조건을 미리 만들어두고(이 단계를 **setup()**이라 부르며 부하
측정에는 포함하지 않는다), VU를 0→10→50→100명까지 늘리며 그 조건들을 반복 조회한다.

**결과**: **실패율 0%.** VU 100까지도 전혀 흔들리지 않았고, p95 응답시간은
추천조회 191ms, 저장목록 181ms였다. 처리량은 초당 약 795건으로, 쓰기 경로(초당 약 30건)의
26배였다. 읽기 경로는 지금 규모에서 사실상 병목이 없다는 뜻이다.

### 4.4 혼합 시나리오 (03_mixed.js)

**목적**: 실제 서비스에서는 조회와 생성이 동시에 섞여 들어온다. 읽기 경로만, 쓰기 경로만
따로 몰아붙인 앞의 두 테스트와 달리, 실제 트래픽에 가까운 비율로 섞어서 동시에 걸었을 때도
문제가 없는지 확인했다.

**방법**: 매 요청마다 무작위로 **읽기 70% / 생성 20% / 재계산 10%** 비율을 뽑아 호출한다.
VU 0→30명까지 5분에 걸쳐 늘린다.

**결과**: 실패율 **0.03%(13/40,674건)**, 처리량 초당 약 135건. write_heavy 단독 테스트보다도
낮은 실패율이 나왔는데, 혼합 환경에서는 쓰기 요청 비중 자체가 낮아 동시에 겹치는 쓰기
트랜잭션 수가 줄어들었기 때문으로 보인다.

### 4.5 브레이크포인트 테스트 (04_breakpoint.js)

**목적**: 앞의 테스트들은 "정해둔 최대치(VU 50, 100, 30)까지는 버틴다"만 확인했다. 그렇다면
**정확히 몇 명부터 무너지는가?** 를 찾기 위한 테스트다.

**방법**: VU를 0명에서 시작해 최대 400명까지 아주 완만하게 계속 늘린다. 그러다가 (1)
에러율이 1%를 넘거나 (2) p95 응답시간이 3초를 넘는 순간, k6가 테스트를 **자동으로 중단**
한다(`abortOnFail` 옵션). 끝까지 다 돌리지 않고 "무너지는 순간"만 잡아내는 방식이다.

**결과**: **VU 약 150명 근처**에서 자동 중단됐다. 흥미로운 점은 **에러 때문이 아니라
레이턴시 때문**이었다는 것이다 — 에러율은 0.09%로 정상이었지만, p95 응답시간이 3.05초로
기준을 넘었고 최악의 경우 17초까지 걸렸다. 즉 VU가 늘어도 요청이 실패하진 않았고, "그냥
계속 느려지기만" 했다.

이 원인을 Prometheus로 실측해서 확인했는데, 6장에서 자세히 다룬다.

### 4.6 소크 테스트 (05_soak.js)

**목적**: 지금까지의 테스트는 전부 몇 분 안에 끝났다. 짧은 시간에는 안 보이지만 **오래
켜두면 서서히 드러나는 문제**(예: 메모리를 계속 잡아먹고 안 돌려주는 "메모리 누수",
DB 커넥션을 계속 열기만 하고 안 닫는 "커넥션 누수")가 있는지 확인하려면 긴 시간 동안
꾸준한 부하를 유지해봐야 한다. 이런 테스트를 **소크 테스트(soak test, "푹 담가두기"
테스트)**라 부른다.

**방법**: VU를 늘렸다 줄였다 하지 않고 **15명으로 고정**한 채 30분간 유지한다
(이런 방식을 **constant-vus**라 부른다. 앞의 램핑 방식과 다르게 사용자 수를 일정하게
유지하는 게 핵심이다). 03_mixed와 같은 읽기70/생성20/재계산10 비율을 쓴다. 30분 동안
인증 토큰이 만료(기본 1시간)되지 않도록, 매 요청마다 토큰을 새로 발급하도록 만들었다.

**결과**: 실패율 **0.05%(128/247,889건)**, 총 247,889회 요청을 처리(초당 약 138건).
Prometheus로 30분 내내 다음을 확인했다:

- **DB 커넥션 수가 30분 내내 11~12개로 완전히 고정** — 커넥션이 계속 쌓이지 않고 정상
  반납되고 있다는 뜻(누수 없음).
- **응답 속도가 초반 2~3분 워밍업 후 27분 내내 거의 변화 없이 평평** — 시간이 갈수록
  느려지는 기색이 없었다(누수가 있었다면 뒤로 갈수록 느려졌을 것이다).
- 앱 컨테이너 메모리는 늘어났지만(이전 8분짜리 테스트 직후 663MB → 이번 30분 테스트 후
  962MB), 이건 자바 프로그램이 부하에 맞춰 정상적으로 메모리를 늘려 쓰는 흔한 동작이고,
  진짜 문제(메모리 부족으로 인한 성능 저하)였다면 위의 "응답 속도가 평평했다"는 결과와
  모순된다. 따라서 심각한 누수로 보지 않는다.

**결론: 30분 동안 성능 저하나 누수 신호 없이 안정적으로 동작했다.**

## 5. 발견한 버그: 동시 생성 요청 시 데이터베이스 데드락

### 5.1 증상

4.2절의 `write_heavy` 첫 실행에서, 동시 사용자가 20명을 넘어서자 조건 생성 요청의 4.37%가
500 에러로 실패했다. 앱 로그를 확인하니 전부 같은 원인이었다:

```text
org.springframework.dao.DeadlockLoserDataAccessException:
Deadlock found when trying to get lock; try restarting transaction
```

### 5.2 원인

추천 결과를 저장하는 `recommendations` 테이블은 어느 행정동(동네)을 추천했는지 기록하는
`admin_dong_id`라는 칼럼을 갖고 있고, 이 칼럼은 "이 값은 반드시 실제 존재하는 행정동을
가리켜야 한다"는 규칙(**외래 키, Foreign Key**)으로 `admin_dongs` 테이블과 연결돼 있다.

DB(MySQL/InnoDB)는 이 규칙을 지키기 위해, `recommendations`에 새 행을 추가할 때마다
"내가 참조하는 그 행정동이 지금 이 순간 삭제되고 있지는 않다"는 걸 잠깐 보장하려고
해당 행정동 행에 짧은 잠금을 건다.

문제는 우리 서비스의 행정동이 서울 전체 426개뿐이고, 추천 점수 계산 로직 특성상 "조건이
좋은" 동네(예: 교통 좋고 편의시설 많은 곳)는 서로 다른 사용자가 서로 다른 조건을 입력해도
자주 똑같이 상위로 추천된다는 점이다. 그러다 보니:

1. 사용자 A의 요청이 `[동네1, 동네2, 동네3, 동네4, 동네5]` 순서로 5개 행을 한 번에 저장하려
   시도하며 동네1의 잠금을 먼저 잡는다.
2. 거의 동시에 사용자 B의 요청이 `[동네2, 동네1, 동네3, 동네4, 동네5]`처럼 **다른 순서**로
   같은 5개 동네를 저장하려 시도하며 동네2의 잠금을 먼저 잡는다.
3. A는 동네2 잠금을 기다리고, B는 동네1 잠금을 기다리는 상태가 된다 — 서로가 서로를
   기다리는 **순환 대기(데드락)**.
4. MySQL이 이 상황을 감지하고, 둘 중 하나의 요청 전체를 강제로 취소(롤백)시킨다. 이게
   앱에서 500 에러로 나타난 것이다.

VU가 적을 때는 이런 충돌이 우연히 일어날 확률이 낮아 안 보이다가, 동시 요청이 많아질수록
확률이 높아져 눈에 띄게 된 것이다. **이건 k6나 스텁 설정 때문이 아니라, 실제 서비스에서
동시 사용자가 많아지면 그대로 재현될 수 있는 진짜 버그였다.**

### 5.3 해결 방법

데드락이 발생하면 DB가 그 트랜잭션(작업 묶음) 전체를 롤백시키기 때문에, 복구하려면
문장 하나만 다시 실행해서는 안 되고 **그 작업 전체를 처음부터 다시 시작**해야 한다.

이를 위해 [DeadlockRetry.java](../src/main/java/com/kbait/anchack/common/util/DeadlockRetry.java)
라는 재시도 유틸리티를 만들어 조건 생성/재계산 API를 감싸도록 했다
([ConditionController.java](../src/main/java/com/kbait/anchack/condition/controller/ConditionController.java)).
데드락 예외(`DeadlockLoserDataAccessException`)가 나면, 시도 횟수에 비례해 잠깐 대기했다가
(재시도들이 또 같은 타이밍에 몰려 데드락을 재생산하지 않도록 무작위 지터도 섞음) 총 3회
시도한다(최초 1회 + 재시도 2회). 3번 다 실패해야만 진짜로 에러 응답을 내려준다.

> 왜 서비스 코드 내부가 아니라 컨트롤러에서 재시도를 걸었는지도 기술적으로 중요한
> 이유가 있다: Spring의 트랜잭션 관리는 "프록시"라는 방식으로 동작하는데, 같은 클래스
> 안에서 자기 자신의 메서드를 다시 호출하면 이 프록시를 거치지 않아 트랜잭션이 새로
> 시작되지 않는다. 그래서 재시도는 그 메서드를 "호출하는 바깥쪽"에서 걸어야 매번 진짜
> 새 트랜잭션으로 재시도된다.

### 5.4 수정 검증

수정 후 `write_heavy`를 다시 돌린 결과, 실패율이 **4.37% → 0.06%**로 떨어졌다(단독 실행
기준. 혼합 시나리오에서는 0.03%). 남은 극소수의 실패도 로그로 확인해보니 총 3회 시도를
다 써버릴 정도로 최고 동시성 구간(VU 50)에서 운 나쁘게 계속 충돌한 극단적인 경우였다.

## 6. HikariCP 커넥션 풀 크기 실험

### 6.1 배경

4.5절의 브레이크포인트 테스트에서, VU 150 근처부터 에러 없이 응답만 느려지는 현상을
발견했다. 이 앱은 DB 커넥션 풀(HikariCP)의 최대 크기를 10개로 설정해뒀는데
([RootConfig.java](../src/main/java/com/kbait/anchack/common/config/RootConfig.java)),
"동시에 DB 작업을 할 수 있는 요청이 10개뿐이라, 나머지는 순서를 기다리며 대기 → 그 대기
시간이 응답 지연으로 나타난 것 아닌가"라는 가설을 세웠다.

### 6.2 실측으로 가설 검증

Prometheus로 MySQL의 실제 연결 수(`threads_connected`)를 추적한 결과, k6가 만든 동시
사용자(VU)는 0명에서 50명까지 계속 늘어나는데도 **MySQL에 실제로 연결된 커넥션 수는
11~12개에서 단 한 번도 움직이지 않았다.** 이는 HikariCP의 `maximumPoolSize=10`(+
모니터링 도구 자체의 연결 1~2개)이 정확히 그 상한을 만들고 있다는 걸 데이터로 직접 확인한
것이다.

### 6.3 풀 크기를 20으로 늘려 재검증

가설이 맞다면 풀을 키우면 더 많은 VU를 버틸 수 있어야 한다. `maximumPoolSize`를 10→20으로
올리고 브레이크포인트 테스트를 다시 돌렸다.

| | 풀 크기 10 | 풀 크기 20 |
|---|---|---|
| 무너진 VU 지점 | 약 150 | 약 151 (**거의 동일**) |
| p95 응답시간(임계값 3초) | 3.05초 | 3.07초 |
| 최대 응답시간 | 16.99초 | 8.56초 (개선) |
| 에러율 | 0.09% | 0.10% |
| MySQL 실제 연결 수 | 11~12 고정 | **최대 22까지 사용** |

풀은 실제로 더 열렸다(11~12 → 최대 22, Prometheus로 확인). 그런데 **정작 무너지는 지점은
거의 그대로**였다. 최대 응답시간이 줄어든 걸 보면(17초→8.6초) 순수하게 "커넥션을 기다리는
줄"은 짧아졌지만, 그렇다고 처리할 수 있는 총량 자체가 늘지는 않았다는 뜻이다.

### 6.4 왜 그랬는가 — HikariCP 권장 공식과의 일치

HikariCP 개발자가 제시하는 적정 풀 크기 공식이 있다:

```text
풀 크기 ≈ (CPU 코어 수 × 2) + 유효 디스크 스핀들 수
```

이 로컬 개발 환경의 CPU는 물리 코어 4개(Intel i5-1135G7), 디스크는 SSD(회전형 디스크가
아니므로 "스핀들 수"는 관례상 1로 둠)다. 공식에 대입하면:

```text
(4 × 2) + 1 = 9
```

**원래 설정값 10이 이미 이 공식의 적정값(9)에 아주 가까웠다.** 즉 처음 설정이 대충 정한
숫자가 아니라, 이 로컬 서버(4코어) 기준으로는 이미 "적정선"이었던 것이다. 20으로 올린 건
이론값의 2배가 넘는 수치였고, 그 결과 **병목이 "커넥션을 기다리는 것"에서 "DB(4코어)가
그만큼의 동시 쓰기 작업을 처리할 CPU 여력이 없는 것"으로 옮겨갔을 뿐**이라고 해석된다.
오히려 동시에 진행되는 쓰기 트랜잭션이 늘어난 만큼 5장의 데드락이 재발할 위험만 커질 수
있다.

### 6.5 결론

**풀 크기를 늘리는 건 이 환경에서 뚜렷한 이득이 없다고 판단해 10으로 되돌렸다.** 판단
근거와 실험 결과는 이 문서와 `test/load-test` 브랜치의 `RootConfig.java` 주석으로 남겨,
나중에 같은 실험을 반복하지 않도록 했다. 진짜 성능을 더 끌어올리려면 풀
크기가 아니라 (1) 캐시 없이 매번 전체 스캔하는 스코어링 쿼리(`MetricScoreMapper`)를
캐싱하거나, (2) DB 서버 자체의 CPU 스펙을 늘리는 쪽이 더 근본적인 방향으로 보인다.

## 7. 모니터링: Prometheus + Grafana

### 7.1 왜 필요했나

k6가 테스트 종료 후 보여주는 요약 결과만으로는 "왜" 느려졌는지 알기 어렵다(5장, 6장의
원인 분석은 전부 Prometheus로 시간대별 데이터를 직접 들여다봐서 가능했다). 그래서 시험
도중 서버 쪽 지표(DB 커넥션 수 등)와 k6 쪽 지표(응답시간, VU 수 등)를 같은 시간축에서
비교할 수 있는 모니터링 스택을 구성했다.

### 7.2 구성

`docker-compose.yml`(`test/load-test` 브랜치)에 아래 세 가지를 `monitoring`이라는 이름의
그룹(profile)으로 묶어 추가했다. 평소 `docker compose up`으로는 안 뜨고, 필요할 때만
`docker compose --profile monitoring up -d`로 켠다(`loadtest/README.md` 참고).

- **mysqld-exporter**: MySQL 서버의 내부 상태(커넥션 수, 슬로우 쿼리 등)를 읽어서 외부에서
  조회 가능한 형태로 변환해주는 도구.
  - 중간에 겪은 문제: 최신 버전(0.20+)이 비밀번호를 담은 접속 정보(DATA_SOURCE_NAME)를 더
    이상 환경변수로 안 받고 `.my.cnf`라는 설정 파일로만 받도록 바뀌어 있었다. 비밀번호를
    git에 커밋되는 파일에 평문으로 넣을 수 없으니, 컨테이너가 시작할 때 그 파일을
    즉석에서 만들어 쓰도록 처리했다.
- **Prometheus**: mysqld-exporter가 내놓는 지표를 5초마다 가져가 저장하는 데이터베이스.
  k6가 직접 밀어넣는(push) 지표도 받을 수 있게 설정했다(`--web.enable-remote-write-receiver`).
- **Grafana**: Prometheus에 쌓인 데이터를 그래프로 보여주는 대시보드. 로컬 전용이라 로그인
  없이 바로 들어가지게(익명 admin 접속) 설정했다.

### 7.3 k6 결과를 Prometheus로 보내기

k6 실행 명령에 `--out experimental-prometheus-rw` 옵션만 붙이면 테스트 중 실시간으로
Prometheus에 지표가 쌓인다:

```bash
k6 run -e JWT_SECRET="$JWT_SECRET" --out experimental-prometheus-rw \
  loadtest/k6/scenarios/01_write_heavy.js
```

Grafana에서는 대시보드 ID **19665**(k6 공식 대시보드)와 **7362**(MySQL Overview,
mysqld-exporter용)를 가져와(Import) 쓰면 바로 그래프를 볼 수 있다.

## 9. 실제 사용자 규모로 VU 추정하기

지금까지의 테스트는 VU 30~150 사이를 다뤘는데, "그 VU 숫자가 실제로 우리 서비스 규모에
비해 큰지 작은지"를 알아야 결과를 올바르게 해석할 수 있다. 팀에서 만든 시장 규모(TAM/SAM/SOM)
추정 자료를 바탕으로, 실제로 기대되는 동시 접속자 수를 역산해봤다.

### 9.1 시장 규모 추정 요약

2025년 국내 20~34세 이동자(이사한 사람) 수를 기준으로 단계적으로 좁혀나간 값이다.

| 단계 | 값 | 의미 |
|---|---|---|
| TAM | 2,230,935명 | 전국 20~34세 국내 이동자 (전체 잠재 시장) |
| SAM | 514,124명 | 그중 서울을 도착지로 한 총전입자 (우리가 노릴 수 있는 시장) |
| SOM (기준 3% 침투율) | 15,424명 | 초기 서비스 침투율 3%를 적용한 실제 확보 가능 사용자 |
| SOM (최대 5% 침투율) | 25,706명 | 공격적인 시나리오 |
| 피크 MAU (3% 기준) | 3,341명 | 이사 탐색 기간(평균 2개월)과 월별 계절성(전입이 몰리는 2~3월)을 반영한, 한 달 사용자가 가장 많은 시점의 추정치 |
| 기준 DAU | 334명 | 피크 MAU의 10% (한 달에 평균 3일 정도 쓰는 수준으로 가정) |
| **부하테스트용 스트레스 DAU** | **501명** | 기준보다 여유 있게 잡은 DAU/MAU 15% 시나리오 |
| 5% 최대 시나리오 스트레스 DAU | 835명 | 침투율 5%(최대) × DAU/MAU 15% |

### 9.2 DAU를 동시 접속자(VU)로 바꾸는 공식

DAU(하루 방문자 수)를 그대로 VU로 쓰면 안 된다. DAU 500명이라고 500명이 항상 동시에 접속해
있는 게 아니라, 하루 중 각자 다른 시간에 흩어져서 짧게 쓰고 나가기 때문이다. 실제 동시
접속자 수는 다음 공식으로 구한다:

```text
동시접속자(VU) = DAU × 피크시간 집중률 × 평균 세션시간(분) / 60
```

- **피크시간 집중률**: 하루 중 가장 사용자가 몰리는 1시간에, 그날 방문자 중 몇 %가
  세션을 "시작"하는지의 비율. 하루 24시간에 완전히 고르게 퍼진다면 1/24≈4%겠지만, 실제
  서비스는 특정 시간대(저녁 시간 등)에 쏠려서 이보다 훨씬 높다.
- **평균 세션시간 / 60**: "그 1시간 동안 시작된 세션들이, 평균적으로 그 시간 안에서 얼마나
  겹쳐 있는지"를 비율로 바꿔주는 부분이다. 세션이 짧을수록 서로 덜 겹치고, 길수록 더
  겹친다.

### 9.3 평균 세션시간 — 비슷한 서비스의 실측치로 보정

이 두 값 중 **평균 세션시간**은 비슷한 서비스(직방/다방/호갱노노 등 부동산 앱)의 공개
통계로 근사할 수 있었다. 모바일 시장 분석 업체 모바일인덱스(igaworks)가 2020년 발표한
리포트에 "부동산 앱 TOP5, 1인당 월평균 사용시간·사용일수" 데이터가 있었다:

| 앱 | 월평균 사용시간 | 월평균 사용일수 | 세션당 시간(사용시간÷사용일수) |
|---|---|---|---|
| 네이버부동산 | 59분 | 6.3일 | 9.4분 |
| 호갱노노 | 41분 | 7.5일 | 5.5분 |
| 직방 | 31분 | 4.2일 | 7.4분 |
| 다방 | 30분 | 2.8일 | 10.7분 |
| 청약홈 | 16분 | 3.5일 | 4.6분 |
| **평균** | | | **약 7.5분** |

(하루에 한 번 켠다고 가정하고 "한 달 사용시간 ÷ 한 달 사용일수"로 세션당 시간을 역산했다.)
이 프로젝트도 부동산/동네 탐색 서비스라 비슷한 사용 패턴일 것으로 보고, **평균 세션시간을
7.5분으로 사용**했다.

반면 **피크시간 집중률**은 공개된 시간대별(hourly) 트래픽 데이터를 찾지 못했다(기업들이
공개하지 않는 경쟁 민감 정보로 보임). 그래서 일반적인 소비자 앱에서 흔히 쓰이는 경험적
범위인 **15~25%**를 가정치로 사용했다. 더 정확한 값은 추가 조사가 필요하다.

### 9.4 계산 결과

```text
VU = DAU × 피크시간 집중률 × (7.5 / 60)
   = DAU × 피크시간 집중률 × 0.125
```

| 피크시간 집중률 | VU (스트레스 DAU 501 기준) | VU (5% 최대 스트레스 DAU 835 기준) |
|---|---|---|
| 15% | 9명 | 16명 |
| 20% | 13명 | 21명 |
| 25% | 16명 | 26명 |

**즉 실제로 기대되는 동시 접속자는 대략 9~26명 사이**로 추정된다.

### 9.5 이 추정치가 의미하는 것

지금까지 실행한 테스트들과 비교하면:

- `write_heavy`(VU 50), `mixed`(VU 30) — 이미 추정 범위(9~26명)를 웃도는 수준으로 테스트함
- `breakpoint`에서 실제로 무너진 지점(VU 약 150) — 추정 최대치(26명)의 **약 5.8배**

**정리하면, 지금까지 진행한 부하테스트는 실제 예상 트래픽 대비 상당한 안전마진(약 5배
이상)을 이미 확인해준 셈이다.** 다만 "피크시간 집중률"이 실측이 아닌 가정치이므로, 더
정확한 근거(비슷한 서비스의 시간대별 데이터, 또는 팀 자체 설문 등)가 확보되면 이 계산은
갱신이 필요하다.

## 10. 종합 결론

1. **읽기 경로(추천 조회, 저장 목록)는 VU 100까지 에러 0%로 매우 안정적이다.** 지금
   데이터 규모에서는 병목이 없다.
2. **쓰기 경로(조건 생성, 재계산)에서 실제 버그(동시 요청 시 DB 데드락)를 발견하고
   수정했다.** 재시도 로직 적용 후 실패율이 4.37%에서 0.03~0.06%로 크게 개선됐고, 이는
   실제 서비스에서도 동시 사용자가 늘면 재현될 수 있었던 문제였다.
3. **VU 150 근처부터 응답이 느려지기 시작하지만, 에러로 이어지지는 않는다.** 원인은
   DB 서버(로컬 환경 기준 물리 4코어)의 처리 한계로 보이며, HikariCP 커넥션 풀 크기를
   늘리는 것으로는 해결되지 않음을 실측으로 확인했다.
4. **30분 소크 테스트에서 메모리 누수·커넥션 누수·성능 저하 신호가 없었다.**
5. **실제 예상 트래픽(동시접속자 약 9~26명) 대비, 지금까지 검증한 범위(VU 30~150)는
   충분한 여유를 갖고 있다.**

## 11. 남은 과제

- **피크시간 집중률의 정확한 근거 확보** — 현재 15~25% 가정치를 팀 자체 조사(설문, 비슷한
  서비스 벤치마크 등)로 보정 필요
- **캐시 없는 스코어링 쿼리(`MetricScoreMapper`) 최적화** — VU 150 이후의 진짜 성능

- **JVM/애플리케이션 레벨 모니터링 추가** — 이 프로젝트는 Spring Boot가 아니라 Spring MVC라
  Actuator/Micrometer가 없어, 지금은 k6 자체 지표와 MySQL 서버 지표만 본다. 힙 메모리·GC·
  스레드풀 등을 보려면 Prometheus JMX Exporter 도입 검토 필요
