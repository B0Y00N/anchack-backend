# 통근 필터 - 카카오 길찾기 API 호출 한도 문제 정리

`destAddress`가 있는 추천 요청에서 통근 조건(`CommuteFilter`)을 계산할 때 겪은 문제와
검토·구현한 해결 방안을 기록한다.

## 문제 상황

- `CommuteFilter`는 `destAddress`가 있으면 하드필터(지역구/필수인프라/예산)를 통과한
  후보 행정동 전부(최대 426개, 서울 전체 행정동 수)에 대해 카카오 대중교통 길찾기
  API(`/v2/routing/publictraffic`)를 실시간으로 호출한다.
- 요청 1건이 이론상 최대 426번의 외부 API 호출을 만들어내는데, 실제 테스트에서 이
  한도를 넘겨 다수의 후보가 `httpStatus=400, {"errorType":"BadRequest","message":"API
  limit has been exceeded.","code":-10}` 로 실패했다(한 요청에서 최대 309/426건 실패,
  이후 재시도에서도 248/426건 실패 등 매번 수백 건 규모).
- 처음엔 "일일 쿼터 소진"으로 추정했으나, 같은 요청을 1시간 이내 간격으로 재시도해도
  실패하는 행정동 조합과 실패 개수가 매번 달랐다(309건 실패 → 이후 248건 실패로
  오히려 감소). 고정된 일일 쿼터가 거의 바닥났다면 반복할수록 성공 개수가 단조 감소해야
  하는데 그렇지 않았다.
- 별도로, 동시 호출이 몰릴 때 순간적인 429(TooManyRequests)도 관찰됐다(같은 요청에서
  14건, 재시도 후 전부 해소되어 429 자체는 큰 비중은 아니었음).

### 정밀 실측: 약 20 req/s의 단기(≈1초 window) 호출 제한

이후 요청 순번(`requestSeq`)·시작/종료 시각을 로깅하도록 계측을 추가해 실패 패턴을
다시 분석했다.

- 실패 로그를 시간순으로 나열하면 무작위가 아니라 **거의 정확히 벽시계 1초 간격으로
  성공 구간과 실패 구간이 반복**됐다(성공 구간 시작 시각이 매번 1.00±0.02초 간격).
  분당 한도가 아니라 **초 단위로 리셋되는 짧은 윈도우 제한**이라는 뜻이다.
- 같은 1초 윈도우 안에 동시에 요청을 몰아넣는 방식(스레드를 요청 개수만큼 만들고
  `CountDownLatch`로 정확히 같은 시각에 동시 출발)으로 10/15/20/25건씩 3회 반복
  테스트한 결과:

  | 동시 요청 수 | 결과 (3회 반복) |
  |---|---|
  | 10 | 10 성공 / 0 실패 (3회 모두) |
  | 15 | 15 성공 / 0 실패 (3회 모두) |
  | 20 | 20 성공 / 0 실패 (3회 모두) |
  | 25 | 20 성공 + 5 실패, 20+5, 18+7 |

  20건까지는 매번 예외 없이 통과하고 25건부터 초과분이 거의 결정적으로 거절되는
  것으로 보아, **현재 이 API 키/환경 기준 실측 상한은 초당 약 20건**으로 판단된다.
- 다만 카카오는 비정상 트래픽 방지를 위해 정확한 임계값을 공식 문서로 공개하지
  않으며(Kakao Developers 쿼터 문서에는 일간/월간 쿼터만 명시, 데브톡 커뮤니티에서도
  "제휴 문의로 별도 안내" 답변만 확인됨), 이 20 req/s는 어디까지나 우리 쪽 실측치다.
  API 키가 바뀌거나 시간이 지나면 재측정이 필요하다.
- 별개로, 위와 같은 정밀 실측과 무관하게 **일일 쿼터도 별도로 존재**한다는 정황을
  나중에 다시 확인했다: 당일 누적 호출량이 매우 많아진 시점에 동일한 pacing으로도
  "앞부분은 성공하다가 특정 시점부터 그 이후 전부 실패"하는 절벽형 패턴이 나타났고,
  API 키를 교체(+ 해당 앱에서 길찾기/주소검색 상품 활성화)한 뒤에는 동일 조건에서
  실패가 사라졌다. `-10 API limit has been exceeded` 메시지는 "초당 한도 초과"와
  "일일 쿼터 소진"을 구분하지 않고 동일하게 내려오므로, 응답만으로는 두 원인을
  구분할 수 없다는 점에 유의해야 한다.

## 이미 적용한 완화책

- **429 재시도**: `KakaoTransitDirectionsClient`/`KakaoGeocodingClient`가 429를 받으면
  500ms 대기 후 1회 재시도. 순간적인 레이트리밋에는 효과 확인(재시도 후 429 재발 0건).
  단, 초당/일일 호출 한도 자체를 줄이는 효과는 없음.
- **소프트 실패 처리**: API 호출이 끝내 실패해도 해당 후보를 하드필터에서 제외하지
  않고 `commuteTime`/`transferCount`를 비운 채 소프트 스코어링으로 넘긴다(요청 전체
  실패를 방지, 근본 해결책은 아님).

## 검토·구현한 해결 방안

### 1. 직선거리(Haversine) 기반 사전 필터 — 채택, 구현 및 실측 검증 완료
목적지 좌표와 후보 행정동 좌표 간 직선거리를 계산해 가까운 순 상위
`MAX_COMMUTE_ROUTE_CANDIDATES`(50)건만 실제 API 호출 대상으로 삼는다
(`CommuteFilter`). 구현이 단순하고 새 인프라가 필요 없다.

- 단점: 행정동 경계나 교통망과 무관한 순수 물리적 거리라, "직선거리는 멀지만
  직행 노선이 있어 실제로는 빠른" 후보를 놓칠 수 있다(50위 밖은 완전성 손실).
  호출량 상한을 완전성보다 우선한 의도적 트레이드오프다.
- 이 직선거리는 실제 통근시간 판단에는 쓰지 않는다 — 순수하게 호출 대상을 좁히는
  사전 필터링 기준일 뿐이며, 최종 통근시간/환승 횟수는 기존과 동일하게 카카오
  길찾기 API 결과를 그대로 사용한다.

### 2. 행정동 경계(GeoJSON) 기반 사전 필터 — 기각
목적지가 속한 구를 point-in-polygon으로 파악해 같은 구 후보만 필터링하는 방식.
`place` 도메인에 이미 있는 `AdminDongBoundaryRepository`(GeoJSON 파싱) 재사용
가능. 기각 사유: 서울 구는 크기/모양이 제각각이라(강남구는 매우 큼, 중구는 작음)
"같은 구"라는 기준이 실제 통근 가능성과 상관관계가 약하다. 인접 구까지 포함하려면
구 인접관계 데이터를 새로 만들어야 해 복잡도만 늘어난다.

### 3. 목적지 행정동 단위 지연(lazy) 캐싱 — 설계는 검토, 이번 범위에서는 보류
목적지 좌표가 속한 행정동을 GeoJSON point-in-polygon으로 파악한 뒤,
`(출발 행정동, 목적지 행정동, 통근수단)` 단위로 통근시간을 캐싱하는 방식. 서로 다른
정확한 주소라도 같은 행정동 안에 있으면 캐시를 공유하므로, 같은 목적지 행정동으로
오는 반복 요청은 API 호출 없이 캐시를 재사용할 수 있다.

- 전체 조합(426×426 ≈ 18만 쌍)을 미리 다 채우는 배치 방식은 그 자체로 18만 번의 API
  호출이 필요해(지금 겪고 있는 문제를 그대로 재현하는 규모) 기각. 실제 요청이 들어올
  때만 필요한 만큼 채워나가는 지연 캐싱만 검토 대상.
- 방안 1(Haversine)과 방안 5(전역 pacing)만으로 현재 트래픽 규모에서는 실패 없이
  처리되는 것을 실측으로 확인했기 때문에, 캐싱은 이번 브랜치 범위에서는 보류하고
  **트래픽이 늘어 다시 문제가 재현될 때 후속 작업으로 진행**한다. DB 스키마 초안은
  별도로 준비했다가 이번 브랜치에서는 제외했다 — 실제 캐싱 구현에 착수할 때 같이
  다시 설계·추가한다.

### 4. 대안 길찾기 API 검토 — ODsay, 후속 검토 대상으로 보류
카카오 API 자체의 호출 한도가 병목이라면, 다른 벤더를 병행/대체하는 것도 고려
대상이다. [ODsay](https://lab.odsay.com)는 전국 대중교통 데이터를 제공하는
길찾기 API로, 카카오와 별도로 검토해볼 만하다.

- **무료(Basic) 티어**: 일 1,000건 호출, 개인/학생/5인 이하 스타트업만 이용 가능,
  6개월 무료. **초당 호출 한도도 별도로 존재하지만 정확한 수치는 카카오와 마찬가지로
  비공개**(비정상 트래픽 방지 목적).
- **유료(Standard 이상)**: 최대 10만 건까지 확장 가능, 사용 기간/호출량 기준 과금.
- **커버리지**: 전국(카카오와 달리 서울에 국한되지 않음 — 다만 우리 서비스는 현재
  서울 한정이라 이 장점은 당장은 크게 중요하지 않음).

**판단**: ODsay Basic의 일 1,000건 한도는 방안 1 적용 후 요청 1건이 만드는 호출량
(최대 50건)보다는 넉넉하지만, 카카오 하나에만 의존하지 않는 이중화 목적이 아니면
지금 당장 도입할 필요는 없다. 카카오 쪽 순간 장애/레이트리밋 시 ODsay를 폴백으로
병행 호출하는 이중화 전략은 후속 검토 대상으로 남겨둔다.

### 5. 애플리케이션 전체 호출 pacing — 채택, 구현 및 실측 검증 완료
`KakaoTransitDirectionsClient`(Spring 싱글턴 빈)에 `AtomicLong` 기반 CAS 슬롯
예약으로, 이 인스턴스를 거치는 **모든 요청을 합쳐서** 최소 80ms 간격(=12.5 req/s)을
강제한다. 방안 1과 별개 계층으로, 한 요청 안에서만이 아니라 **동시에 여러 사용자
요청이 들어와도 애플리케이션 전체 합계가 안전 마진(실측 상한 20 req/s 대비
12.5 req/s) 안에 머물도록** 보장한다.

- 설계 근거(한 문장): 실측 결과 대중교통 경로 API는 현재 환경에서 약 20 req/s
  부근의 단기 호출 제한이 관찰되었으므로, 안전 마진을 두어 애플리케이션 전체
  호출을 약 12.5 req/s로 pacing하고, 동시에 추천 요청 1건의 최대 외부 API
  fan-out을 Haversine 기반 50건으로 제한한다.
- `COMMUTE_CALL_CONCURRENCY=10`(기존 값 유지), 429 500ms 재시도(기존 로직 유지)와
  함께 동작한다.

## 실측 검증 결과

방안 1(Haversine 50건 캡) + 방안 5(전역 80ms pacing) 구현 후 실제 컨테이너에서
검증했다.

| 테스트 | 결과 |
|---|---|
| 단일 요청 50건 | 49 성공 + 경로없음 1 = 50/50, 실패 0건, 429도 0건 (4.69초, 이론값 50/12.5≈4초와 일치) |
| **동시 사용자 2명(50+50=100건)** | 양쪽 배치 각각 49 성공 + 경로없음 1 = **100/100, 실패 0건, 429도 0건** (각 ~8초, 이론값 100/12.5≈8초와 일치) |

동시 요청 테스트에서 두 배치의 pacing 슬롯을 시간순으로 합치면 오차 없이 80ms
간격(`0, 79, 158, 237, 317, 397, 477, 556, ...ms`)으로 이어진다 — 두 사용자의
요청이 완전히 하나의 전역 큐로 직렬화된다는 뜻이며, "요청 1건이 아니라
애플리케이션 전체 합계가 12.5 req/s인지" 검증하려던 목적에 정확히 부합한다.

## 다음 액션

방안 1(Haversine 50건 캡)과 방안 5(전역 80ms pacing)를 1차 대응으로 구현·실측
검증까지 완료했다. 방안 3(지연 캐싱)은 트래픽이 늘어 방안 1+5만으로 부족해지는
시점에 후속으로 진행하고, 방안 4(ODsay 병행)는 캐싱 도입 이후 효과를 측정해보고
필요성을 재평가한다.
